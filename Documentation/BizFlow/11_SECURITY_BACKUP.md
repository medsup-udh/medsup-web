# 11 — ความปลอดภัยและการสำรองข้อมูล (Security & Backup)

> สถานะ: Phase 0 — แผนเพื่อตรวจรับ · อ้างอิงสถาปัตยกรรม `10_SYSTEM_ARCHITECTURE.md` (Stack B — รอ D-02)
> ค่าตัวเลข (ระยะเวลา session, พารามิเตอร์ hash ฯลฯ) เป็นข้อเสนอเริ่มต้น ปรับได้ใน Phase 1 โดยไม่ลดระดับความปลอดภัย
> ความสามารถของผู้ให้บริการที่ระบุว่า "ตามที่ผู้ให้บริการระบุ" ยังไม่ได้ตรวจกับหน้าทางการ — **แผนนี้ไม่พึ่งพาสิ่งเหล่านั้นเป็นการรับประกันหลัก**: การรับประกันการกู้คืนมาจากสำเนาที่เราควบคุมเองและการทดสอบ restore

## 1. สิ่งที่ต้องปกป้อง (Assets) และผู้คุกคาม

| ทรัพย์สิน | ความสำคัญ | ผลหากเสียหาย |
|---|---|---|
| ใบกำกับภาษี/เอกสารที่ออกแล้ว + PDF ต้นฉบับ | สูงสุด (หลักฐานภาษี ≥ 5 ปี) | ตรวจสอบภาษีไม่ได้, เลขที่ขาดช่วง |
| ข้อมูลลูกค้า (ชื่อ ที่อยู่ เลขผู้เสียภาษี ผู้ติดต่อ) | สูง (ข้อมูลส่วนบุคคล) | รั่วไหล → PDPA (OI-L01) |
| ข้อมูลการเงิน (ยอดขาย ลูกหนี้ บัญชีธนาคารที่แสดงในเอกสาร) | สูง | ความลับทางธุรกิจ |
| บัญชีผู้ใช้เดียว (OWNER) | สูงสุด (จุดเดียวที่เข้าถึงทุกอย่าง) | ยึดระบบ ออกเอกสารปลอม |
| Audit log และ hash chain | สูง | หลักฐานว่าไม่มีใครแก้ย้อนหลัง |
| คีย์เข้ารหัสสำรองข้อมูล | สูงสุด | **สูญหาย = กู้คืนจากสำรองไม่ได้** |

### 2.1 รหัสผ่านและการยืนยันตัวตน

| หัวข้อ | ข้อกำหนด |
|---|---|
| การเก็บ | Argon2id (ข้อเสนอเริ่มต้น: หน่วยความจำ 64 MiB, 3 รอบ, 1 ขนาน) พร้อม salt ต่อผู้ใช้; ไม่เก็บรหัสผ่านที่อ่านได้ ไม่ใส่ใน log |
| นโยบาย | ยาว ≥ 12 ตัวอักษร ไม่บังคับอักขระพิเศษ; ปฏิเสธรหัสที่อยู่ในรายการรหัสยอดนิยม/ที่เคยรั่ว (ตรวจแบบที่ไม่ส่งรหัสผ่านออกนอกระบบ) |
| MFA | TOTP บังคับ (D-10) + รหัสสำรอง 10 ชุด (เก็บแบบ hash, ใช้ได้ครั้งเดียว) |
| ป้องกันการเดา | จำกัด 5 ครั้งผิดต่อบัญชี+IP ใน 15 นาที แล้วหน่วงเวลาเพิ่มขึ้น (ไม่ล็อกถาวร เพื่อกันการโจมตีให้ผู้ใช้เข้าไม่ได้); ข้อความผิดพลาดเหมือนกันทุกกรณี |
| การเปลี่ยน/ลืมรหัสผ่าน | ลิงก์ครั้งเดียว อายุ 30 นาที ส่งอีเมล; เปลี่ยนแล้วยกเลิกทุก session; แจ้งเตือนอีเมลเมื่อเปลี่ยนรหัสหรือ MFA |
| การแจ้งเตือน | อีเมลเมื่อเข้าสู่ระบบจากอุปกรณ์/ประเทศใหม่ |

### 2.2 Session

คุกกี้ `__Host-session` · `HttpOnly` · `Secure` · `SameSite=Lax` · ค่าสุ่ม 256 บิตที่เก็บฝั่งเซิร์ฟเวอร์ (ยกเลิกได้ทันที) · หมดอายุเมื่อไม่ใช้งาน 30 นาที / สูงสุด 12 ชั่วโมง · หมุนค่า session เมื่อเข้าสู่ระบบและเมื่อยืนยัน MFA · ปุ่ม "ออกจากระบบทุกอุปกรณ์" · การกระทำสำคัญ (เปลี่ยนรหัส, ปิด MFA, ดาวน์โหลดข้อมูลทั้งหมด) ต้องยืนยันรหัสผ่านซ้ำ · ป้องกัน CSRF ด้วย `SameSite` + ตรวจ `Origin` + โทเค็นในคำสั่งเขียนข้อมูล

### 2.3 การสื่อสาร

HTTPS เท่านั้น (TLS 1.2 ขึ้นไป, ใบรับรองอัตโนมัติ), HSTS 1 ปี, ปิดพอร์ต HTTP หรือ redirect, ฐานข้อมูลและ storage รับเฉพาะ TLS และจำกัด IP/เครือข่ายส่วนตัวเท่าที่ผู้ให้บริการรองรับ

Header มาตรฐาน: `Content-Security-Policy` (ไม่อนุญาต inline script — ใช้ nonce; `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy` ปิดสิ่งที่ไม่ใช้

### 2.4 การตรวจข้อมูลนำเข้า การฉีดคำสั่ง และ XSS

| ภัย | มาตรการ |
|---|---|
| ข้อมูลผิดรูปแบบ | Schema (Zod หรือเทียบเท่า) ทุกจุดรับข้อมูล: ชนิด, ความยาว, ช่วงค่า, enum; เซิร์ฟเวอร์ไม่เชื่อค่าจากเบราว์เซอร์ (รวมยอดเงิน — TR-11) |
| SQL injection | ใช้ parameterized query เท่านั้น; ห้ามต่อสตริง SQL (lint rule + code review); role ของแอปไม่มีสิทธิ์ DDL/superuser |
| XSS | React escape เป็นค่าเริ่มต้น; ห้าม `dangerouslySetInnerHTML` กับข้อมูลผู้ใช้; CSP แบบ nonce; หมายเหตุ/ชื่อที่ผู้ใช้กรอกแสดงเป็นข้อความเสมอ |
| ข้อมูลที่ถูกนำไปสร้าง CSV/Excel | ป้องกัน CSV injection: ค่าที่ขึ้นต้นด้วย `=`, `+`, `-`, `@` ใส่ `'` นำหน้า |
| อักขระไทย/ยูนิโค้ด | ปรับรูปแบบ (NFC), ตัดอักขระควบคุม, จำกัดความยาว — ทดสอบด้วยสระซ้อน/ZWSP เพื่อไม่ให้ทำ PDF พัง |

### 2.5 การสร้าง PDF ปลอดภัย (ข้อมูลผู้ใช้ถูกใส่ลงในเอกสารที่ Chromium render)

1. Escape ข้อมูลทุกช่องก่อนใส่แม่แบบ HTML (ใช้เอนจินแม่แบบที่ escape อัตโนมัติ)
2. ปิด JavaScript ในหน้าที่ render PDF
3. บล็อกคำขอเครือข่ายทั้งหมดจากหน้านั้น — ฟอนต์และรูปโลโก้โหลดจากไฟล์ในเครื่อง/ข้อมูลฝังเท่านั้น (ป้องกัน SSRF และการอ่านไฟล์ `file://`)
4. รัน Chromium ด้วยผู้ใช้สิทธิ์ต่ำใน container แยก, timeout 30 วินาทีต่อฉบับ, จำกัดหน่วยความจำ, 1 เพจต่อครั้ง
5. ข้อมูลที่ใช้ render มาจาก **snapshot ของเอกสาร** ไม่ใช่ข้อมูลหลักปัจจุบัน (BR-PRT-04)

### 2.6 การบันทึก Log และข้อมูลส่วนบุคคล

แยก **audit log** (ในฐานข้อมูล, เก็บ ≥ 10 ปี, แก้ไม่ได้) ออกจาก **application log** (เก็บ 30–90 วัน) · application log ห้ามมี: รหัสผ่าน, token, session id, เลขผู้เสียภาษี, ที่อยู่ลูกค้า, เนื้อหาเอกสาร · error tracking ภายนอกต้องตัดข้อมูลเหล่านี้ก่อนส่ง · Audit log บันทึก IP และ user agent (เพื่อตรวจสอบ)

### 2.7 การควบคุมการเข้าถึง

ทุก route/API ต้องผ่าน session ที่ตรวจแล้ว (ปฏิเสธโดยค่าเริ่มต้น — deny by default) · บทบาท OWNER (ทำได้ทุกอย่าง) และ VIEWER (อนาคต, อ่านอย่างเดียว) บังคับที่ชั้น service ไม่ใช่แค่ซ่อนปุ่ม · ไม่มีหน้าสมัครสมาชิกสาธารณะ (FR-AUTH-03) · ไม่มีบัญชีใช้ร่วมกัน · บัญชีผู้ดูแลระบบโครงสร้างพื้นฐาน (เซิร์ฟเวอร์, DB, storage) เปิด MFA ทุกบัญชี

### 2.8 ความปลอดภัยของฐานข้อมูล

Role แยกตามหน้าที่ (`app_rw`, `migrator`, `readonly_reports`, `backup_ro`) · `app_rw` ไม่มีสิทธิ์ `UPDATE/DELETE/TRUNCATE` บน `audit_logs`, `product_price_history`, `document_revisions` และ trigger ซ้ำอีกชั้น (`04`) · เปิด `statement_timeout` และจำกัดจำนวน connection · ห้ามเปิดฐานข้อมูลสู่อินเทอร์เน็ตสาธารณะ

## 3. การเก็บไฟล์อย่างปลอดภัย

| หัวข้อ | ข้อกำหนด |
|---|---|
| Bucket | private ทั้งหมด; ไม่เปิดการ list สาธารณะ |
| ชื่อ object | ไม่เปิดเผยข้อมูลลูกค้า; ใช้ `docs/{ปี}/{ประเภท}/{เลขที่}_{variant}_v{n}.pdf` (เลขที่เอกสารไม่ใช่ความลับ แต่การเข้าถึงต้องผ่านสิทธิ์) |
| การดาวน์โหลด | ผ่านเซิร์ฟเวอร์ตรวจ session → ออก signed URL อายุ ≤ 5 นาที พร้อม `Content-Disposition: attachment` |
| การเขียนซ้ำ | PDF canonical ห้ามเขียนทับ (ไม่มี overwrite — สร้างเวอร์ชันใหม่); ตรวจ sha256 ทุกครั้งที่อ่านเพื่อดาวน์โหลด |
| การเข้ารหัส | เข้ารหัสขณะพัก (at rest) ตามผู้ให้บริการ — ตามที่ผู้ให้บริการระบุ ต้องตรวจ; สำเนาสำรองเข้ารหัสเองก่อนอัปโหลด (§6) |
| การอัปโหลดโลโก้ | PNG/JPG เท่านั้น ≤ 1 MB, ตรวจชนิดไฟล์จากเนื้อหา, แปลงใหม่ (re-encode) ลบ metadata; **ข้อเสนอ: ไม่รับ SVG** เพราะฝังสคริปต์ได้ (Spec FR-CO-03 ระบุ SVG — ต้องได้รับอนุมัติเป็น D-23 ก่อนจึงจะตัดออก; ถ้าต้องรับ SVG ต้อง sanitize แบบ allow-list และแปลงเป็นภาพ raster ก่อนใช้) |
| ไฟล์ชั่วคราว | PDF รวม/export อายุ 24 ชม.–7 วัน ลบอัตโนมัติ (`expires_at`) |

## 5. ความเป็นส่วนตัวของข้อมูล (PDPA)

ข้อมูลส่วนบุคคลในระบบ: ชื่อ ที่อยู่ โทร อีเมล ของผู้ติดต่อลูกค้า (และบุคคลธรรมดาที่เป็นลูกค้า) · ข้อมูลในเอกสารภาษีที่ออกแล้วต้องเก็บตามกฎหมายแม้ลูกค้าขอลบ (snapshot) · สิ่งที่ลบ/ปิดบังได้เมื่อเลิกติดต่อ คือข้อมูลผู้ติดต่อใน `customer_contacts` · **ข้อกำหนดแจ้งเหตุละเมิด การประกาศความเป็นส่วนตัว และฐานทางกฎหมาย ยังไม่ได้ศึกษา — เป็นประเด็น OI-L01 ห้ามถือว่าเป็นข้อสรุป** · ข้อมูลทดสอบใช้ข้อมูลสมมติเท่านั้น

| ข้อมูล | วิธี | ความถี่ | เก็บไว้ | RPO ที่ได้ |
|---|---|---|---|---|
| ฐานข้อมูล (logical) | `pg_dump -Fc` → บีบอัด → เข้ารหัส (age/GPG) → B2 + ตรวจ sha256 | รายชั่วโมง 07:00–22:00 (เวลาไทย) + รายคืน 02:00 | รายชั่วโมง 48 ชม.; รายวัน 35 วัน; รายเดือน (วันที่ 1) 24 เดือน; รายปี 10 ปี | ≤ 1 ชม. ในเวลาทำการ; ≤ 24 ชม. นอกเวลา |
| ไฟล์ PDF/โลโก้ | sync เฉพาะ object ใหม่ → B2 (ไม่ลบฝั่งสำรองเมื่อต้นทางหาย — append-only) | ทุกชั่วโมง + ตรวจรายคืน | ตามอายุเอกสาร (≥ 10 ปี) | ≤ 1 ชม. |
| การตั้งค่าโครงสร้างพื้นฐาน | `ops/` (docker-compose, Caddyfile, สคริปต์) อยู่ใน Git; คีย์/ความลับสำรองแยกในที่เก็บรหัสผ่าน | ทุกการเปลี่ยนแปลง | ตลอดไป | — |
| สำรองก่อนเปลี่ยนโครงสร้าง | dump เฉพาะกิจก่อนรัน migration ทุกครั้ง | ทุก deploy ที่มี migration | 90 วัน | — |

เป้าหมายตาม NFR-10: **RPO ≤ 24 ชม. (ขั้นต่ำ) — แผนนี้ให้ ≤ 1 ชม. ในเวลาทำการโดยไม่ต้องเสียค่า PITR เพิ่ม** (ฐานข้อมูลเล็ก การ dump รายชั่วโมงใช้ทรัพยากรน้อย; ถ้าขนาดข้อมูลโตจนไม่เหมาะ ให้เปลี่ยนไปใช้ WAL archiving) · **RTO ≤ 4 ชม.** (วัดจริงในการซ้อม §8.2)

### 6.3 การเข้ารหัสและคีย์ (จุดล้มเหลวที่พบบ่อย)

- เข้ารหัสด้วย public key (age) บนเซิร์ฟเวอร์ — **เซิร์ฟเวอร์ไม่ถือ private key** เพื่อให้ผู้บุกรุกเซิร์ฟเวอร์ถอดรหัสสำเนาสำรองไม่ได้
- Private key เก็บ 3 ที่: ที่เก็บรหัสผ่านของผู้ว่าจ้าง, อุปกรณ์/ไฟล์ออฟไลน์ที่เข้ารหัส, สำเนากระดาษในที่ปลอดภัย
- ทดสอบถอดรหัสทุกครั้งที่ซ้อมกู้คืน (§8) · **ถ้าสูญเสียคีย์ทั้ง 3 ที่ สำเนาสำรองทั้งหมดใช้ไม่ได้** — เหตุผลที่ต้องเก็บหลายที่
- สิทธิ์เขียน B2 ของเซิร์ฟเวอร์: เขียนอย่างเดียว ลบ/เขียนทับไม่ได้ (ใช้ application key แบบจำกัด + object lock/retention หากรองรับ — ต้องตรวจ) เพื่อกัน ransomware ลบสำเนา

### 6.4 การแจ้งเตือนเมื่อสำรองล้มเหลว

ทุกงานสำรองบันทึกใน `backup_runs` · แจ้งอีเมลเมื่อ: งานล้มเหลว, ไม่มีงานสำเร็จเกิน 3 ชม. ในเวลาทำการ, ขนาดไฟล์ต่างจากค่าปกติ > 30%, ตรวจ checksum ไม่ผ่าน, ซ้อมกู้คืนล้มเหลว · Dashboard (S-02) แสดงสถานะสำรอง/ซ้อมกู้คืนล่าสุด (FR-SET-05)

## 7. ขั้นตอนกู้คืน (Recovery Runbook — ต้องทำตามได้โดยไม่ต้องจำ)

### RB-1 ฐานข้อมูลเสียหาย/สูญหาย (เซิร์ฟเวอร์ DB ใช้ไม่ได้)

| ขั้น | การกระทำ | ผลที่ต้องได้ |
|---|---|---|
| 1 | ประกาศหยุดระบบ: ตั้งหน้า "กำลังบำรุงรักษา" (ปิดการเขียน) บันทึกเวลาที่เริ่มเหตุการณ์ | ไม่มีข้อมูลใหม่เข้า |
| 2 | ระบุจุดที่ต้องกู้ถึง: ค่าเริ่มต้น = dump รายชั่วโมงล่าสุดที่ผ่านการตรวจ; ถ้าสงสัยข้อมูลถูกแก้โดยผู้ไม่หวังดี ให้เลือกจุดก่อนเหตุ | จุดกู้ที่ตัดสินใจแล้ว |
| 3 | ดึงไฟล์ dump จาก B2 + ไฟล์ checksum ตรวจ sha256 | checksum ตรง |
| 4 | ถอดรหัสด้วย private key | ได้ไฟล์ `.dump` |
| 5 | สร้างฐานข้อมูล PostgreSQL ใหม่ (เวอร์ชันเดียวกัน) + role ตาม `ops/` | ฐานข้อมูลเปล่า |
| 6 | `pg_restore` (ไม่ใช้ superuser ของแอป) | สำเร็จไม่มีข้อผิดพลาด |
| 7 | **รันชุดตรวจความถูกต้อง** (`04` §10): ความต่อเนื่องเลขที่, content_hash, hash chain, ผลรวมการจัดสรร ≤ ยอดใบกำกับภาษี, จำนวนแถวเทียบ `backup_runs.verification` | ทุกข้อผ่าน |
| 8 | ตรวจไฟล์: object ที่ `document_files` อ้างถึงมีครบและ sha256 ตรง (สุ่ม 100 หรือทั้งหมดถ้าน้อยกว่า) — ที่ขาดให้กู้จาก B2 | ไม่มีไฟล์ขาด |
| 9 | ชี้แอปไปฐานข้อมูลใหม่ (เปลี่ยน secret ฐานข้อมูล) แล้วทดสอบแบบอ่านอย่างเดียวโดย OWNER: เปิดเอกสาร 5 ใบและดาวน์โหลด PDF — ยังไม่ออกเอกสารใหม่จนกว่าจะผ่านขั้น 7–8 | ใช้งานได้ |
| 10 | เปิดระบบ; บันทึกเหตุการณ์ใน `backup_runs` (RESTORE_DRILL หรือ INCIDENT) และ audit; **ข้อมูลที่เกิดหลังจุดกู้ถึงต้องบันทึกใหม่จากเอกสารกระดาษ/อีเมล** (ระบบแสดงรายชื่อเอกสารที่หายไปโดยเทียบเลขที่กับเอกสารที่ส่งลูกค้าแล้ว — เลขที่ขาดช่วงในลำดับคือหลักฐาน) | |
| 11 | ทบทวนเหตุการณ์ (post-incident) ภายใน 7 วัน; อัปเดตเอกสารนี้ | |

### RB-2 เซิร์ฟเวอร์แอปเสียหาย (DB ยังอยู่)

สร้างเซิร์ฟเวอร์ใหม่จาก `ops/` (Docker image + docker-compose + Caddyfile) → ใส่ความลับจากที่เก็บ → ชี้ DNS → ตรวจ `/healthz` · เป้าหมายภายใน 1 ชม.

### RB-3 สงสัยบัญชีถูกยึด

1. ออกจากระบบทุกอุปกรณ์ + เปลี่ยนรหัสผ่านและ MFA จากอุปกรณ์ที่เชื่อถือได้
2. หมุนคีย์ทั้งหมด (session secret, DB, storage, backup write key)
3. ตรวจ audit log ช่วงเวลาที่สงสัย + ตรวจ hash chain; ตรวจเอกสารที่ออก/ยกเลิกในช่วงนั้น
4. ถ้ามีการแก้ข้อมูลที่ไม่ใช่ของผู้ใช้ → ใช้ RB-1 เลือกจุดก่อนเหตุ
5. ประเมินหน้าที่แจ้งเหตุละเมิดข้อมูลส่วนบุคคลกับที่ปรึกษากฎหมาย (OI-L01)

### RB-4 ลบเอกสารหรือข้อมูลผิดพลาด

ระบบไม่ลบเอกสารที่ออกแล้ว (ยกเลิกเท่านั้น) · ถ้าลบข้อมูลหลัก (ลูกค้า/สินค้า) ผิด: ปิดใช้งานแทนลบ (ย้อนได้); ถ้าจำเป็นต้องกู้จาก dump ให้ restore ลงฐานข้อมูลชั่วคราวแล้วดึงเฉพาะแถวที่ต้องการ

## 8. การทดสอบกู้คืน (Restore Testing) — ไม่ใช่แค่ตรวจว่ามีไฟล์

### 8.1 ทดสอบอัตโนมัติรายสัปดาห์ (งาน `RESTORE_TEST`)

1. ดึง dump รายคืนล่าสุดจาก B2 → ตรวจ sha256 → ถอดรหัสด้วย **key สำหรับทดสอบ** (key ทดสอบแยก; ใช้ private key จริงเฉพาะเวลาซ้อมใหญ่)
2. restore ลงฐานข้อมูลชั่วคราว
3. ตรวจสอบ: (ก) จำนวนแถวต่อตารางตรงกับค่าที่บันทึกตอน dump; (ข) ผลรวม `grand_total` ของ INV ISSUED รายเดือนตรงกับค่าบันทึก; (ค) เลขที่ต่อเนื่อง; (ง) hash chain; (จ) สุ่มอ่านเอกสาร 20 ฉบับพร้อม snapshot และคำนวณยอดด้วย Tax Engine ซ้ำได้ค่าเท่าเดิม; (ฉ) สุ่มตรวจ sha256 ของ PDF 20 ไฟล์จาก B2
4. ลบฐานข้อมูลชั่วคราว · บันทึกผลใน `backup_runs` · แจ้งเตือนเมื่อไม่ผ่านข้อใดข้อหนึ่ง

### 8.2 ซ้อมใหญ่ทุกไตรมาส (และก่อน go-live — Phase 4)

สร้างระบบใหม่ทั้งหมดบนเซิร์ฟเวอร์เปล่าตาม RB-1 + RB-2 โดย **ผู้ที่ไม่ใช่คนเขียนสคริปต์** ทำตามเอกสารอย่างเดียว · จับเวลาทุกขั้น · เกณฑ์ผ่าน: ครบ RTO ≤ 4 ชม., ผ่านทุกข้อตรวจในขั้น 7–8 ของ RB-1, ไม่ต้องถามคนเขียน · ผลที่ล้มเหลวให้แก้เอกสาร/สคริปต์แล้วซ้อมซ้ำ · บันทึกผลใน `backup_runs` (RESTORE_DRILL)

### 8.3 สิ่งที่ถือว่า "ยังไม่มีสำรอง"

สำเนาที่ไม่เคยถูก restore สำเร็จภายใน 90 วันที่ผ่านมา · สำเนาที่ถอดรหัสไม่ได้ · สำเนาที่อยู่ในบัญชีเดียวกับข้อมูลจริง
